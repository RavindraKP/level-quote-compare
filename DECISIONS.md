# Decisions

One line each: decision — reason.

- WP0: Model-facing schemas carry prices, multiples and slab bounds as strings exactly as written; code parses them — the model transcribes, it never converts or computes (non-negotiable 2).
- WP0: Money and quantities are stored as TEXT decimal strings and handled as `Decimal` in code — SQLite has no exact decimal type and floats would drift.
- WP0: Timestamps are fixed-width UTC ISO strings (`db.now_iso()`) — string comparison then orders them correctly (used for heartbeat staleness).
- WP0: SQLAlchemy engine uses `NullPool` — every `connect()` is a fresh SQLite connection, so no connection is ever shared across threads.
- WP0: Added `invitation` (rfx, vendor, status) and `price_history` tables to the PLAN §5 schema — "awaiting" columns and "same as last year" need them.
- WP0: Added flag type `unreadable` — PLAN §5 "Real-world files" requires a review item for files that cannot be read.
- WP0: Job dedupe uses a partial unique index on `kind:target:file_hash` for queued/running jobs only — a finished or failed job never blocks a retry, so "retry" is just `enqueue` again.
- WP0: Stale jobs are re-queued at start-up and on every idle worker loop (heartbeat every 3 s, stale after 15 s, failed after 3 attempts) — a quick restart can leave a fresh-looking heartbeat that start-up alone would miss; the attempt cap stops a crashing job looping.
- WP0: Job handlers register with `@handler("kind")` in `level/jobs.py`; the worker imports that module at start — one place to find every job kind. WP2 adds its handler there.
- WP0: The worker starts on the first page load after a server start (Streamlit has no start-up hook) — queued jobs wait until someone opens the app.
- WP0: `app/Home.py` is the router (passcode gate, start-up, `st.navigation`); the home content is `app/pages/0_Overview.py` — the gate then runs once before every page.
- WP0: Passcode gate is off when `LEVEL_PASSCODE` is unset — local development without friction; the hosted app must set it.
- WP0: `llm.complete` defaults to effort `medium`, set explicitly — Haiku 5.5's default is `medium` and the plan asks for it to be explicit; callers lower or raise per step.
- WP0: `llm.structured` validates the model's JSON with Pydantic itself rather than relying on the SDK's parse — a schema mismatch becomes a clear `InvalidOutputError`, and `stop_reason` is checked first.
- WP0: `level` is installed as a package (hatchling) — Streamlit pages, scripts and tests all import it without path tricks.
- WP4: Renamed `app/pages/` to `app/views/` — with a folder named `pages` next to Home.py, Streamlit 1.67 falls back to v1 multipage mode for the whole process when the first request after a start is a deep link (e.g. a refresh on /Inbox): Home.py never runs, so the gate, wide layout and worker start-up are skipped. File names inside are unchanged.
- WP4: Screens read SQLite through `app/components/data.py` (no Streamlit inside); the three hooks owned by other packages (cell rebuild, pipeline job kind, clarification draft) are bound in `app/components/backend.py`, currently to `mock_backend.py` — switching to WP2/WP3 is a one-file change.
- WP4: Mock demo event (`app/components/mock_seed.py`) is invented safety-supplies data, not the evaluation dataset; it generates its own XLSX/PDF/DOCX/PNG so the source viewer can be exercised. The mock pipeline job never invents prices: it walks the stages and opens an "unreadable: not connected" flag.
- WP4: A buyer's review decision is stored as JSON in `flag.resolution` ({"action": confirm|edit_value|not_quoted|apply_fix, "value", "note"}) and the cell rebuild reads it — review never edits a cell or claim directly. WP3's cells.py should honour this contract.
- WP4: Grid footer totals and "lowest eligible" are display helpers in `components/data.py` (Decimal, unit-tested); they should call level/core once WP3 exposes equivalents — non-negotiable 2 wants totals in core.
- WP4: "Lowest eligible" = confirmed or inferred cell from a vendor whose gating verdict is not "fail"; needs-review and conflict cells are never starred.
- WP4: A vendor who replied but has no cells yet shows as "awaiting" ("reply received but not read yet"), never "not quoted" — not quoted is a finding, not a default.
- WP4: One pipeline job per reply, target `message:<id>`, dedupe hash over body + file hashes — a double-click or refresh returns the same job.
- WP4: Grid cell selection uses `st.dataframe(selection_mode="single-cell")` (Streamlit 1.67); receipt opens beside the grid in one click.
- WP4: pytest `pythonpath` includes `app` so tests can import `components`.
- WP5: The co-pilot runs a short explicit tool loop on `llm.complete(tools=...)` instead of the SDK `tool_runner` — every model call stays in the one wrapper (app key, explicit base_url, streaming, refusal/max_tokens checks); the loop is ~30 lines and every call is logged to `tool_call`.
- WP5: Tools are `strict: true` with `tool_choice` left at auto (forced tool choice is rejected on current models); effort set explicitly to `medium`.
- WP5: Each turn sends a fresh JSON snapshot of the draft plus the code's completeness issues; earlier turns are replayed as plain text — direct edits are always seen, and the draft in SQLite stays the single source of truth.
- WP5: Tools change only the fields they are given (null = unchanged), keyed by line_no / q_no — chat and direct edits cannot overwrite each other. The page's data editors apply only Streamlit's edit delta, and editor keys include the draft's latest audit id so they reload after any change.
- WP5: `import_from_history` copies lines from the newest earlier event that has lines — the plan has no separate "history event" table; `price_history` holds prices, `rfx_line` holds specs.
- WP5: Completeness is category-neutral: each line needs a unit, an annual quantity and a non-empty spec (the generic form of "dimensions/weight"); gating questions need a pass rule (`<=, <, >=, >, ==, is_yes, valid_on_date`); terms need price_basis, currency, payment_days, delivery; at least one vendor invited.
- WP5: The co-pilot has no send tool. Send is a button gated by a "reviewed" checkbox; `draft.send` is idempotent (a draft only), writes one outbox email per invited vendor with the Excel template attached, and sets the RFx to issued.
- WP1: PDFs are rendered with PyMuPDF's HTML `Story` engine, not Playwright — Python Playwright is not installed in the project and PyMuPDF is already a dependency; output is real text PDFs.
- WP1: Ground truth "unit_price_inr" is INR per canonical unit, ex-GST, before conditional discounts; "landed_price_inr" = unit + stated freight (null when freight is unknown). Payment-term carrying cost is not baked in; evals compute it from `cost_of_capital` (annual, simple interest on days different from the requested 60).
- WP1: Line order is shuffled per seed (buyers list by SKU) — so seeds differ in which line numbers are 7-ply, missing, or deviating, not only in prices.
- WP1: Per-kg conversion factor is stored as `conversion_factors = {"g_per_piece": "<grams>"}` (`g_per_set` for the partition line, canonical unit "set") — matches the example in db.py.
- WP1: Gating pass rules are stored as JSON: Q1 `{"op": "valid_on", "value": <award date>}`, Q2 `{"op": "==", "value": "yes"}`, Q8 `{"op": "<=", "value": "10"}`; the award date is also in `rfx.terms.award_date`.
- WP1: Vendor D answers its questionnaire tersely in the email body (not a second handwritten photo) — keeps one photo for the vision path; the expired ISO certificate carries X17.
- WP1: FX placeholder USDINR 86.70 as of 2025-02-24 (assumption table) — candidate to verify before recording.
- WP1: History is written per seed (`data/history/seed-<S>/fy25_contract.json`) and also embedded in ground truth — seed B has different FY25 suppliers.
- WP1: Fictional email domains use `.example` — no chance of naming a real company's domain.
- WP1: Seed B is not generated or committed in this package; QA runs `scripts/generate_dataset.py --seed B` when WP9 says so. The held-out vendor is generated (`--heldout`) and committed, and was not opened.
- WP1: tests/test_dataset.py generates a fresh dataset into a temp dir to check the documents and designed outcomes — it never reads the committed fixtures.
- WP7: The harness calls the system only through `evals/adapters.py`: `level.pipeline.run.process_message(message_id)`, `level.core.cells.rebuild_cells(rfx_id)`, `level.agents.analyst.ask(rfx_id, question) -> str | .text` — WP2/WP3/WP6 had not named these yet; a missing one is reported as "not built", never faked.
- WP7: Each eval run uses its own fresh database under `evals/results/work/` (seeded from fixtures), never the app's database — runs are repeatable and cannot damage demo data.
- WP7: A cell counts as correct within 0.5% of truth (or unpriced where truth is not quoted); needs_review/conflict counts as "correctly flagged"; wrong + confirmed is a silent error. A shown zero is never "not quoted".
- WP7: Expected analyst answers are recomputed in `evals/expected.py`, independent of `level/core`, so a core bug cannot hide itself; landed = unit + freight, carrying cost = price x cost_of_capital x (60 - payment days) / 365 — WP3 should match or the eval will say so.
- WP7: Model grader only for "declined appropriately" (`level.llm.structured`, effort low); numbers and vendor names are graded in code with lakh/crore scaling.
- WP7: `evals/fake.py` writes cells/flags/terms/answers straight to a throwaway database to prove the scoring catches planted mistakes — never used for a real scorecard; fake runs are labelled FAKE and git-ignored.
- WP7: `evals.run` refuses seed B and the held-out vendor without `--allow-unseen` — they run once, when QA says so.
- WP3: Unit conversion is a small unit graph: built-in edges (kg↔g, dozen↔each…) plus each line's `conversion_factors` keys of the form `<unit>_per_<unit>` ({"g_per_piece": "412"}); a breadth-first search finds the chain — category-neutral, and every hop becomes a ConversionStep.
- WP3: Factors are applied as multiply or divide by the stated number, never by a reciprocal — keeps 30 per pack ÷ 6 exactly 5.
- WP3: A quoted unit word we do not know ("box", "roll") is assumed to be one of the line's unit, recorded as an assumption (cell Inferred) — the T4 plausibility check then catches a wrong assumption (≈100×); a known unit with no path (per kg, no weight) is not converted and needs review.
- WP3: Only price-side assumptions (unit factor, FX, GST, history) make a cell Inferred; landed-only inputs (cost of capital, unstated payment days) are recorded but do not change the state.
- WP3: A claim whose evidence check has not passed (`evidence_ok` not true) is never Confirmed unless an evidence flag was closed by a person or the buyer corrected the price (non-negotiable 3).
- WP3: Review resolutions the grid understands: flag closed with `resolution` "not_quoted" or "corrected:<price as written>" — WP4 writes these; anything else just closes the flag.
- WP3: Later message supersedes earlier per vendor × line (X23); within one message, a line-scope claim beats a rule claim beats a reference claim.
- WP3: Gating excludes vendors only on "fail"; "unclear" vendors stay in scenarios with a caveat — unclear is not pass, but excluding it would treat it as fail (X22).
- WP3: "Unconfirmed" in scenarios = inferred, needs review or conflict; "pessimistic" adds 10%; sensitivity exposure = 10% × price × annual qty.
- WP3: Scenarios recompute cells in memory (`compute_cells(snapshot, fx_override, apply_conditional_discounts)`) instead of scaling stored numbers — one code path, and FX what-ifs stay exact when freight is in INR.
- WP3: Scenario hand-computed tests use a small hand-built event in tests/, not seed-A ground truth (off limits outside scripts/ and evals/); WP7 can run the same `solve` on ground truth.
- WP3: Views are (re)installed by `level.core.views.install()`, called from `rebuild_cells` — db.py (WP0) stays untouched.
- WP2: Contract additions in `types.py`: `ExtractedRow.quantity/amount`, `ExtractionOutput.document_kind/stated_totals`, and new model-facing schemas `DocumentFacts` (certificates/reports), `SecondReadOutput` (T2), `ZoomReadOutput` (zoom re-read) — T3 needs the amounts and totals as written; certificates need their own small schema.
- WP2: The job unit is a whole reply (`pipeline.process_message`, target = message id), not one attachment — the email body and its attachments are matched together, and re-running a reply clears exactly what its earlier runs produced.
- WP2: Pages call `run.ingest(...)` then `run.enqueue(message_id)`; the same two calls serve email, upload and reply link, so every channel takes one code path.
- WP2: A plain text PDF goes to the model natively; when any page is a scan or carries a picture, text pages go as labelled text and pictures/scans take the image path — nothing is read twice.
- WP2: Images are kept at native resolution up to 2576 px on the long edge (the high-resolution vision limit in the claude-api skill) and JPEG-encoded only if a PNG exceeds 5 MB; zoom tiles are a 2×2 grid with 15% overlap cut from the unscaled image.
- WP2: Image decision rule: both reads agree → evidence_ok (the double read is the image's evidence check); reads differ → read_mismatch flag with every candidate, even if the zoom agrees with one (it only says which is likelier); "hard to read" alone opens a flag unless the zoom re-read matches.
- WP2: T1 accepts a quote found in a different block than cited (the receipt's locator is corrected to where it was found), except for spreadsheet cell addresses, which must match exactly — model paragraph numbers drift by one; a cell address does not.
- WP2: A stated total is checked only against a complete row sum and never when labelled sub-total or tax-inclusive; a mismatch is a critical attachment-level flag, not a conflict on every cell — the checks cannot tell which line is wrong.
- WP2: Grid-level flags (plausibility, unknown landed price, assumed unit, unconvertible unit) carry no run id and are recomputed for the whole RFx after every reply — a new reply changes the peer median; a flag a person already closed is not reopened.
- WP2: A rule or reference claim with no price is kept as a claim; "the rest" with no lines listed is expanded by code to every line no other row in the reply prices.
- WP2: Clarification drafts use fixed wording per flag type, not the model — a draft can then never carry a number the checks did not produce, and plausibility reasons (which cite peer prices) are replaced by neutral wording for vendors (non-negotiable 10).
- WP2: Added `pillow-heif` (HEIC photos) and `xlrd` (.xls) to dependencies — both formats are on PLAN §5's supported list.
- WP2: Test documents are my own, generated by `tests/wp2_docs/make_docs.py` for a non-packaging RFx (safety supplies, units each/pair); offline tests replace model calls with fixed outputs, `tests/test_pipeline_live.py` makes real calls on two of them.
- WP6: The analyst runs a short explicit tool loop on `llm.complete(tools=...)`, like the co-pilot — every call stays in the one wrapper (app key, explicit base_url, streaming, refusal checks).
- WP6: One definition of landed everywhere: landed = price + freight (grid, scenarios, analyst, matching the ground truth). The payment-terms carrying cost is an explicit option (`ScenarioParams.include_payment_terms`, `compute_cells(include_payment_terms=)`), shown with the cost-of-capital rate as an assumption when used — the grid and the analyst disagreeing on 'landed' would itself be a trust failure. Contract change in `types.py`.
- WP6: Every total, difference and exposure the analyst or Award page shows comes from `level/core/summary.py` (pure, tested); `compare_scenarios` gives differences so the model never subtracts (non-negotiable 2).
- WP6: `query_data` may read only the `v_*` views and the base tables they are built from (SQLite authorizer); SQLite flattens views, so the view name alone cannot be checked. Vendor documents, claims, chat and audit are unreadable; the connection is also `mode=ro` + `query_only`.
- WP6: T9 grounding exempts whole numbers 0–10 and numbers the buyer typed — they are counts and references, not produced figures; everything else must round from a tool number at the precision written (lakh/crore/%/share scaling).
- WP6: Analyst email drafts use fixed wording by code (`missing_lines`, or `clarify.draft_clarification`); the model cannot write email text, so a draft can never carry a price or another vendor's data. Negotiation drafts are left out (PLAN §11).
- WP6: Tables and charts are built by code from a stored tool result id (`show_table`/`show_chart` name columns, not values); chart data is converted to numbers only for drawing.
- WP6: Award drafts (never sends) one clarification per vendor with open vendor-closable flags, not repeated on a second award; the memo's page one lists unconfirmed allocated prices with 10% exposure.

- Integration: Screens bound to the real backend; `mock_backend.py` kept only for `tests/test_ui_data.py`, whose mock event has cells but no claims. Job target is the message id as a string, matching `level.pipeline.run`.

- Fix (WP3 landed): a distance in a freight term ("free within N km") is a condition, not a charge — it was read as ₹150 per piece.
- Fix (WP2 T1): table-cell separators (`|`, tab) are layout, not content — PDF text puts one cell per line while the model quotes the row joined by " | ", so every PDF table row failed the evidence check.

- Fix (WP3 normalise): a generic count word ("per pc", "per 1000 nos") on a line counted in its own item unit ("set") is one item, Inferred with the assumption shown; never for "pair" (two pieces by definition).

- Integration: Inbox "Read again" re-runs the whole pipeline on a reply (idempotent) for the live re-read in the demo; time-to-grid is measured from when the reply reached Level, not the email's own date.
